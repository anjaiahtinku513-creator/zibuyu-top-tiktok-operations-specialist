# Zibuyu Studio · 制作与发布

一个运行在本机的 Zibuyu TikTok 服装视频生产界面。网页负责收集商品图、模特、货号和生产要求；实际分析与制作由本机已登录的 Codex CLI 执行。项目不需要、也不保存 OpenAI API Key。

## 发布中心

通过左侧「发布中心」或交付详情的「进入发布中心」使用。发布状态独立于制作状态，发布失败不会覆盖已交付成片。

1. 制作期间可保存账号、TikTok 商品 PID、账号当地日期，以及「仅交付」偏好，不查询平台或阻塞制作。
2. 成片交付后，网页执行当前安装插件的 `build_publish_handoff.py`。要求本次通过整批校验，不能用旧快照或 `delivered` 状态代替。
3. 展示每个颜色的最终视频、验收结论与完整五标签文案。用户核对后开始准备排期。
4. 使用六个指定账号、命名时区和当地 07:00 / 12:00 / 18:00。超过三条必须明确选择分多日发布；已有台账占用额度和时段。
5. 最终发布表按内容哈希绑定授权，逐条记录请求与提交声明。返回 ID 后只核对结果，服务中断不会自动重发。

**已确认发布规则（2026-09-11）：** `video_title` 传完整文案＋5个唯一标签；账号当地时区按具体日期夏令时换算为北京时间 `+08:00` 后排期。裸时间的 PopBoom 查询结果按此北京时间契约核对；无需重复确认这两项。仍核对账号、PID、视频身份和防重台账，不把排期创建称为已经发布。

现阶段集成范围是工作台创建的生产批次。不会扫描并猜测其他目录中的成片，也不会为独立视频伪造生产台账。核对发布结果需点击「核对发布结果」；本版不宣称关闭本机服务后仍能主动监控。平台接受的定时任务由平台执行。

发布数据位于 `<run>/publishing/`，包括 delivery-snapshot、delivery-review、manifest、approval、dispatch-claim、ledger 与独立的 publishing/web 会话。确定未派发的失效授权归档到 history；派发不明的原记录保留并阻止重试。

## 视觉与技术参考

采用浅色内容面、系统字体、蓝色主要操作，玻璃用于导航、顶部栏与固定进度 Dock；内容与长文案保留高可读的白色底。支持窄屏布局、键盘焦点、减少动画及减少透明度偏好，模糊不可用时使用实色降级。保留现有 React 19 / Tailwind 4 / Base UI / shadcn 依赖，没有为折射效果加入额外渲染运行时。

## 启动

首次从 GitHub 下载后，需要 Node.js 22.13 或更高版本、npm、可用的 Python，以及已登录的 Codex CLI。先安装仓库中的插件，再在本目录安装网页依赖：

```powershell
npm ci
```

直接双击：

```text
start-workbench.cmd
```

或在 PowerShell 中运行：

```powershell
.\start-local.ps1
```

启动器会在后台常驻运行网页和只监听 `127.0.0.1` 的本地桥接服务，健康检查通过后自动打开 `http://127.0.0.1:4318/`。关闭启动终端不会再中断连接；Codex 桌面端与本地桥接是两个独立进程。

需要前台查看开发日志时运行：

```powershell
.\start-local.ps1 -Foreground
```

## 工作流

1. 资料校验
2. 商品分析
3. 生成三视图
4. 三视图质检
5. 脚本与配音
6. 生成前校验
7. 等待付费确认
8. PopBoom 生成
9. 成片质检与交付

创建制作单只启动前 6 步。任务在第 7 步停住，直到用户在页面中审核并明确确认 PopBoom 生成。授权范围、颜色和准备产物哈希会先写入 `approval.json`，再续跑同一 Codex 会话。

准备完成由执行器在结构化产物清单落盘后确认；代理的提前完成进度只显示“正在整理准备产物与授权清单”。页面同时检查准备结果及执行状态，产物清单就绪后才开放付费确认，避免准备收尾期间误报产物缺失。

正式编译包由服务器在准备完成、授权和派发前调用当前插件校验器复验，要求有效、可新提交、哈希稳定且匹配模特/市场/输出/颜色。代理手写的 preflight passed 不能作为通过依据；付费阶段只消费该正式清单。提交前失败的修复保留原授权和派发历史，续跑需明确的新用户指令、独立审阅的原始日志和新产物指纹。旧失败派发只能兑换一次恢复；未知提交与已有平台记录不走这条恢复路径。

每次提交新的制作单都会创建一个独立 Codex 会话，绝不复用上一批上下文。每个批次固定使用 `gpt-5.5` 和 `high` 推理强度；付费确认只会续跑该制作单自己的会话。

如果服务在 PopBoom 提交附近中断，任务会进入 `submission_unknown`，并禁止自动重试，避免重复扣费。

## 本地数据

默认任务目录：

```text
%USERPROFILE%\.codex\zibuyu-runs\<run-id>\
```

每个任务保留原始上传、`intake.json`、阶段事件、Codex JSONL、结构化结果、授权回执和交付产物。

可选环境变量：

```text
ZIBUYU_RUNS_ROOT       自定义任务目录
ZIBUYU_CODEX_WORKSPACE Codex 执行工作区
ZIBUYU_EXECUTOR_MODE   real 或 mock
CODEX_CLI_PATH         显式指定 Codex CLI
ZIBUYU_PYTHON          显式指定发布交付校验使用的 Python
```

`mock` 只用于本地验收，不会调用生成服务。

# 用量记录（2026-09-07）

每次 CLI 执行将独立记录在任务的 `web/usage/<attempt-id>.json`，制作准备、生成/质检和发布各阶段及失败尝试均保留。颜色识别在其自己的批次下记录，关联制作单时单独展示。制作单详情新增 Token 用量表，显示原始 CLI 回报、模型/推理档位和执行耗时。

当前只识别顶层 `turn.completed.usage`，保存每条原始回执与事件序号。缺失字段为 null；缓存是输入的一部分，推理是输出的子项（仅在回报时记录）。续跑累计语义与子代理覆盖尚未核实，因此不计算跨阶段 Token 总和、不推算账单/订阅额度或节省比例。未结束及失败进程可能缺少最终用量；历史任务不补造数据。工具次数按可识别工具 item ID 去重，校验返工次数尚未自动归因。

记录功能不启动新模型任务，也不改变每批独立的 `gpt-5.5 / high` 策略。完整的生产/付费/发布状态仍以原台账和授权为准。
# 同批多模特

固定模特支持同时选择美1/美2/美3/德1/德2/德3中的1–6位，每个颜色使用全部所选模特：C个颜色 × M位模特 = C×M条计划视频。商品图片只需上传一次；跨US/DE时分别填写商品链接，缺失市场来源不会从另一市场复制。自定义模特保留单独制作方式。

一次提交形成一个网站多模特批次，按模特创建独立单模特制作单、Codex会话和付费授权。队列按批次归组，详情可切换同批模特；每次确认只授权当前模特的颜色。所有同批模特完成真实交付校验后，才允许分别准备发布。

### 共享准备与并行（2026-09-07）

多模特制作改为：公共商品分析/市场证据与每色三视图准备一次 → 验收并封存 → 最多三位模特同时准备各自脚本、口播、身份绑定与编译。公共准备拥有独立会话，模特会话通过明确的文件交接复用资料。单模特提交仍支持原流程。

公共资料按本批 SKU、颜色、实际源图 SHA、市场/语言/完整来源 URL、要求和 `shared-preparation-v1` 合约建立指纹，保存在 `_shared/<model-batch>/<fingerprint>/`。同款三视图供各模特复用，US/DE 市场证据只交给相应市场。每个子单得到独立字节副本和来源清单；源图、清单、产物、视觉验收或市场匹配异常时阻断，不自动回退为重复生成。共享规则变化时必须升级合约版本并重新验证。

这是准备阶段的三路并发；付费 Codex 会话另走单通道队列，可与其他模特的准备同时推进。该通道不宣称控制其他入口或整个 PopBoom 账户的渲染并发量。每次付费启动前重核授权指纹和产物字节，先独占写入派发声明。存在派发日志、声明或用量记录的中断任务只核对，不自动重发；可证明从未派发的已授权排队任务可以恢复。

运行时会话 ID、最近活动、执行日志以及公共准备阶段会实时显示在详情中。后台 `codex exec` 会话不会自动注册为 Codex 桌面侧栏任务。重启仅自动恢复尚未执行的完整准备单；已有会话的准备中断保留产物，需要明确的本地续跑记录，按原会话恢复。

旧批次只允许从已完成准备且有历史源图快照、匹配图片字节和完整身份审计的产物迁移；保留原验收及未验证边界，不把旧编译包或测试 fixture 当作公共事实。

完整multipart验证成功后才保存并提交整组任务。原图为各制作单保留独立副本及SHA，不使用可互相改写的硬链接。`_model-batches/`只保存网站分组，不替代插件的单模特`batch-plan/compile/ledger`。新表单通过请求ID避免网络重试创建重复批次；中断后未确认提交完成的请求保持待核对，不自动重发。

## 颜色识别修复（2026-09-07）

颜色识别的结构化输出使用接口支持的 schema，图片只能归入一组的规则由本地校验执行。失败时保留本次 Codex 的具体错误，避免仅显示退出码；重复的最长颜色名也不会使归类卡住。六张原图的只读复测返回三个颜色组，每组两张，无遗漏或重复。当前工作台共 46 项测试通过。
